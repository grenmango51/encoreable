## 6. Root Mechanical Cause of the Divergence

1. **Turn 1 Imprison Activation & Choice Scarf Lock**:
   - `p1a: Indeedee` used `Imprison` (`>p1 move imprison, move protect`).
   - `p1a: Indeedee`'s moveset is `Expanding Force`, `Hyper Voice`, `Imprison`, `Protect`.
   - In Showdown (`data/moves.ts: imprison.condition.onFoeDisableMove`), Imprison calls `pokemon.disableMove(moveSlot.id, true)` on foes for each shared move.
   - Setting `isHidden = true` marks `moveSlot.disabled = 'hidden'` for `Expanding Force` and `Protect` on `p2b: Indeedee`.
   - Concurrently, `p2b: Indeedee` held `Choice Scarf` and executed `Expanding Force` (`>p2 move highhorsepower +2, move expandingforce +1`).
   - Choice Scarf added volatile `choicelock`, locking `p2b: Indeedee` into `Expanding Force` and explicitly disabling its other three moves (`Mystical Fire`, `Trick`, `Protect`) with `disabled = true`.

2. **Turn 2 Request Generation & Player Choice in `playMimic`**:
   - In `sim/pokemon.ts: getMoveRequestData()`, Showdown generates the request for `p2b: Indeedee`. Because `p2b: Indeedee` is in position 1 (last active Pokémon), `isLastActive()` is `true`, setting `restrictData = true`.
   - Under `restrictData = true`, `disabled === 'hidden'` is evaluated as `disabled = !restrictData = false`.
   - Thus, the request sent to player `p2` presented `Expanding Force` as `disabled: false` (with `maybeDisabled: true`), while the other 3 moves were `disabled: true`.
   - In `playFuzz`, player `p2` (`MimicPlayer`) selected:
     `raw: 'switch 4, move 1 2'` (switch Excadrill to Sneasler; Indeedee uses move 1, Expanding Force).

3. **Choice Validation & Input Log Generation in Showdown (`playFuzz`)**:
   - In `sim/side.ts: Side.prototype.chooseMove()`, Showdown validates the submitted move against `pokemon.getMoves()`.
   - During this internal check, `pokemon.getMoves()` is called with no arguments (`restrictData` is `undefined`).
   - When `restrictData` is `undefined`, `!restrictData` evaluates to `true`. Consequently, `disabled === 'hidden'` becomes `disabled = true`.
   - Since all 4 moves on `p2b: Indeedee` are disabled (`Expanding Force` disabled by Imprison; `Mystical Fire`, `Trick`, `Protect` disabled by Choice Scarf), `moves` is empty (`moves.length === 0`).
   - In `sim/side.ts` (lines 465–473 in compiled JS / 699–709 in TS):
     ```typescript
     } else if (!moves.length) {
       if (this.battle.gen <= 4) this.send('-activate', pokemon, 'move: Struggle');
       if (pokemon.maybeLocked) this.choice.cantUndo = true;
       this.choice.actions.push({
         choice: 'move',
         pokemon,
         moveid: 'struggle',
       });
       return true;
     }
     ```
     Showdown accepts the choice, overriding `move 1 2` to `{ choice: 'move', pokemon, moveid: 'struggle' }`.
   - At turn commit (`sim/battle.ts: commitChoices`), Showdown serializes the executed choices via `side.getChoice()`.
   - For `moveid: 'struggle'`, `getChoice()` produces `"move struggle"`.
   - Showdown appends this string directly into `battle.inputLog`:
     `>p2 switch 4, move struggle` (line 8).
   - In Turn 3, the exact same sequence repeated, writing:
     `>p2 move flamethrower +1, move struggle` (line 11).

4. **Rejection during Replay in `replayInputLog`**:
   - In `scripts/local-score.mjs`, `replayInputLog` feeds the generated `played.inputLog` line-by-line into a fresh `BattleStream`.
   - At Turn 2, `stream.write('>p2 switch 4, move struggle')` is executed.
   - Showdown's `Side.prototype.chooseMove('struggle')` validates the string `'struggle'` against `request.moves`.
   - `request.moves` contains only `['expandingforce', 'mysticalfire', 'trick', 'protect']`. It does not contain `'struggle'`.
   - Showdown emits a choice rejection:
     `Can't move: Your Indeedee doesn't have a move matching struggle`.
   - Because `side.choice.error` is raised, `p2`'s Turn 2 choice is never committed (`isChoiceDone = false`).
   - Subsequent lines in `inputLog` fail with cascading choice errors. Turn 2 never begins executing.
   - Replay terminates at line 41 (`|turn|2`), leaving `replayed.channels[1]` truncated at 42 lines vs 127 lines in `played.ch1`.
   - `same` evaluates to `false`, causing the engine to log `CRASH: the input log does not replay the battle`.

5. **Engine Discrepancy Between `reconstruct.mjs` and `fuzz.mjs`**:
   - `scripts/lib/reconstruct.mjs` (lines 1255–1266) explicitly accounts for this Showdown inputLog serialization bug by intercepting `battle.inputLog.push`:
     ```javascript
     // A move a hidden disable turned into Struggle - Imprison's, in doubles - is
     // recorded as `move struggle`, which the request it answered never offered,
     // so that line would be refused on replay. The
     // choice that was written is recorded in its place.
     const written = {};
     const recordInput = battle.inputLog.push;
     battle.inputLog.push = function (line, ...rest) {
       const m = /^>(p[1-4]) (.*)$/.exec(String(line));
       const raw = m && written[m[1]];
       const fixed = raw && /\bmove struggle\b/.test(m[2]) && !/\bstruggle\b/.test(raw) ? `>${m[1]} ${raw}` : line;
       return recordInput.call(this, fixed, ...rest);
     };
     ```
   - However, `scripts/lib/fuzz.mjs` (`playFuzz`), which executes `playMimic`, does not install this interceptor. As a result, the unreplayable `move struggle` strings generated by Showdown remain in `played.inputLog`.
